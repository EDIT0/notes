## 0-12. Kotlin lazy vs lateinit

- **`lazy`** : `val` 위임 프로퍼티. 처음 접근하는 시점에 한 번만 초기화되고, 이후엔 캐시된 값을 재사용. 기본적으로 **스레드 안전**
- **`lateinit`** : non-null `var` 프로퍼티를 선언 시점이 아니라 **나중에 외부에서 초기화**할 때 사용 (의존성 주입, 생명주기 콜백 등). 초기화 전에 접근하면 `UninitializedPropertyAccessException` 발생

```kotlin
val lazyValue: String by lazy {
    println("Computed once")
    "Hello, Lazy"
}
println(lazyValue)   // 여기서 초기화 발생 + "Computed once" 출력
println(lazyValue)   // 캐시된 값만 재사용, 람다는 다시 실행 안 됨

lateinit var message: String

fun setupMessage() {
    message = "Hello, Lateinit"
}

setupMessage()
println(message)     // 초기화 후에만 안전하게 접근 가능
```

---

- **주요 차이점**

| | `lazy` | `lateinit` |
|---|---|---|
| 적용 대상 | `val`만 가능 | `var`만 가능 |
| 초기화 시점 | 처음 **접근할 때** 자동 초기화 | **명시적으로** 값을 대입해야 함 |
| 스레드 안전성 | 기본적으로 안전 (모드 변경 가능) | 보장 없음, 직접 신경 써야 함 |
| 초기화 전 접근 시 | 자동으로 초기화되어 문제 없음 | `UninitializedPropertyAccessException` 발생 |
| 적합한 경우 | 계산 비용이 크거나 드물게 쓰이는 읽기 전용 값 | DI, 프레임워크 생명주기처럼 외부에서 나중에 값을 주입받는 경우 |

---

- **Pro Tip: `::property.isInitialized`로 초기화 여부 확인**
  - `lateinit` 프로퍼티에만 사용 가능. 접근 전에 초기화 여부를 확인해 예외를 미리 방지

```kotlin
lateinit var message: String

fun main() {
    if (::message.isInitialized) {
        println("Message is initialized: $message")
    } else {
        println("Message is not initialized yet")   // 처음엔 이 분기
    }

    setupMessage()
    if (::message.isInitialized) {
        println("Message is initialized: $message") // 이제는 이 분기
    }
}
```

---

- **Pro Tip: `lateinit`이 바이트코드로 컴파일되는 방법**
  - `lateinit var config: Configuration` → 평범한 **nullable Java 필드**(`private Configuration config;`)로 컴파일됨. 즉 "약속"을 필드 자체가 지키는 게 아님
  - 진짜 안전장치는 **getter**에 있음 : 값을 반환하기 전에 `if (config == null) throwUninitializedPropertyAccessException(...)` 검사가 삽입됨
  - setter는 평범한 Java setter (그냥 필드에 대입)
  - `::config.isInitialized`는 개념적으로 `this.config != null` 검사로 컴파일됨

```kotlin
class Service {
    private lateinit var config: Configuration   // 실제로는 nullable 필드로 컴파일됨

    fun initialize(c: Configuration) { config = c }     // 평범한 setter 호출
    fun doWork() = println(config.settings)             // getter에서 null 체크 후 반환
}
// 개념적으로:
// Configuration getConfig() { if (config == null) throw UninitializedPropertyAccessException(...); return config; }
```

## 🔑 정리: 특징 · 장단점 · 예시

### 특징
- `lazy`는 "값을 어떻게 만들지"에 집중한 지연 초기화, `lateinit`은 "값을 언제 채워 넣을지"를 외부에 맡기는 지연 초기화
- 둘 다 "선언 시점에는 값이 없고, 나중에 채워진다"는 공통점이 있지만 통제권의 방향이 반대 (lazy는 람다가 자동으로 값을 만들고, lateinit은 누군가가 직접 대입해줘야 함)

### 장점
- `lazy` : 비용이 큰 초기화를 실제로 필요한 시점까지 미루면서도, 스레드 안전성과 캐싱을 공짜로 얻음
- `lateinit` : 생성자에서 당장 줄 수 없는 의존성(Android의 `View`, DI로 주입되는 객체 등)을 non-null 타입으로 유지하면서 다룰 수 있음 (불필요한 `?`/`!!` 없이)

### 단점
- `lazy`는 `val`에만 쓸 수 있어, 값을 나중에 다시 바꿔야 하는 경우엔 쓸 수 없음
- `lateinit`은 초기화를 깜빡하면 런타임에 `UninitializedPropertyAccessException`이 터짐 — 컴파일러가 막아주지 않으므로 사용 전 초기화를 개발자가 책임져야 함
- `lateinit`은 primitive 타입(`Int`, `Boolean` 등)에는 사용할 수 없음 (참조 타입만 가능)

### 예시
```kotlin
class UserViewModel {
    // 생성 시점엔 알 수 없고, 화면 진입 후 비동기로 받아오는 값 → lateinit
    lateinit var userId: String

    // 호출될 때마다 다시 계산할 필요 없는 무거운 포매터 → lazy
    private val dateFormatter by lazy { java.text.SimpleDateFormat("yyyy-MM-dd") }

    fun bind(id: String) {
        userId = id
    }
}
```
