## 0-19. Kotlin 함수형(SAM) 인터페이스

- **함수형 인터페이스(SAM, Single Abstract Method)** : 추상 메서드가 **정확히 하나**뿐인 인터페이스. `fun interface`로 선언하면 람다 표현식으로 바로 구현할 수 있음

```kotlin
fun interface Greeter {
    fun greet(name: String): String
}

val greeter = Greeter { name -> "Hello, $name from skydoves!" }
println(greeter.greet("Kotlin"))   // Hello, Kotlin from skydoves!
```

- **SAM 변환** : 람다를 함수형 인터페이스의 구현으로 자동 취급해주는 메커니즘. Kotlin이 정의한 인터페이스뿐 아니라 **Java의 함수형 인터페이스**(`Runnable` 등)에도 동일하게 적용됨

```kotlin
val runnable = Runnable { println("Running with SAM conversion!") }
runnable.run()   // 명시적 익명 클래스 구현 없이 람다로 바로 전달
```

---

- **주요 특징**
  - 람다 친화적 : 장황한 익명 클래스 대신 람다 하나로 구현 가능
  - 원활한 상호운용성 : Kotlin/Java 양쪽에서 정의된 함수형 인터페이스 모두에 동일하게 작동
  - 보일러플레이트 감소 : 인터페이스 구현을 위한 클래스 선언이 사라짐

---

- **Pro Tip: SAM 변환의 철학 — 왜 이 기능이 필요했나**
  - Java 8 람다 이전에는, 메서드에 "동작"을 전달하는 유일한 방법이 **익명 내부 클래스**였음 (단 한 줄의 로직을 위해 클래스 선언 전체를 작성해야 했음)
  - 핵심 통찰 : **추상 메서드가 하나뿐인 인터페이스는 본질적으로 함수 시그니처와 같다** (`Runnable`은 `() -> Unit`과 구조적으로 동일)
  - Kotlin은 이 통찰을 바탕으로, 람다가 SAM 인터페이스 자리에 전달되면 컴파일러가 바이트코드 수준에서 필요한 익명 클래스를 **자동으로 생성**해줌 → 개발자는 함수형 코드를 쓰고, 생성된 바이트코드는 기존 Java 생태계와 100% 호환됨
  - `fun interface`로 직접 선언하면, Java 상호운용을 넘어 **Kotlin-to-Kotlin API**에서도 똑같은 이점(람다로 호출 가능한 API)을 누릴 수 있음

```kotlin
fun interface ActionHandler {
    fun handleAction(action: String)
}

fun performAction(handler: ActionHandler) { /* ... */ }
performAction { action -> println("Handling: $action") }   // 인터페이스를 람다로 바로 전달
```

## 🔑 정리: 특징 · 장단점 · 예시

### 특징
- "메서드 하나뿐인 인터페이스 = 함수"라는 구조적 동일성을 이용해, 객체지향 인터페이스와 함수형 람다 사이를 이어주는 다리 역할
- SAM 변환은 Kotlin 코드에서만 통하는 트릭이 아니라, Java의 함수형 인터페이스까지 포괄하는 상호운용 장치

### 장점
- 콜백/리스너 스타일 API(특히 Java 기반 라이브러리, Android 리스너 등)를 익명 클래스 없이 람다로 깔끔하게 호출 가능
- `fun interface`를 직접 선언하면, 내가 만든 API도 람다 친화적으로 설계할 수 있음
- 추상 메서드가 하나뿐이라는 제약이 "이 인터페이스는 단일 동작을 나타낸다"는 의도를 코드로 명확히 드러냄

### 단점
- 추상 메서드가 정확히 하나여야 하므로, 여러 동작을 묶어야 하는 인터페이스에는 적용할 수 없음 (그 경우 일반 인터페이스나 sealed interface가 더 적합)
- SAM 변환이 생성하는 익명 클래스(또는 그에 준하는 객체)는 호출마다 새로 만들어질 수 있어, 아주 빈번한 호출 경로에서는 약간의 오버헤드가 생길 수 있음
- Java와의 호환을 위해 사용하는 경우, 어떤 인터페이스가 SAM으로 인식되는지(Java 쪽 어노테이션 유무 등)를 파악하지 못하면 왜 람다로 호출이 안 되는지 헷갈릴 수 있음

### 예시
```kotlin
fun interface Validator<T> {
    fun isValid(value: T): Boolean
}

fun <T> validateAll(items: List<T>, validator: Validator<T>): Boolean =
    items.all { validator.isValid(it) }

val allPositive = validateAll(listOf(1, 2, 3)) { it > 0 }   // 람다로 바로 구현 전달
```
