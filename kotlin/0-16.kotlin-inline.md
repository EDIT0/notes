## 0-16. Kotlin inline

- **`inline`** : 함수를 호출하는 대신, 호출 지점에 **함수 본문(+전달된 람다)을 그대로 삽입**하는 컴파일러 최적화. 람다를 위한 객체 생성과 가상 호출(`invoke()`) 오버헤드를 제거

```kotlin
// 인라인 아님: 람다가 Function 객체로 만들어지고, invoke()로 가상 호출됨
fun nonInlinedAction(block: () -> Unit) {
    println("Before action")
    block()
    println("After action")
}

// inline: 호출 지점에 block()의 코드가 그대로 복사됨 (객체 생성/가상 호출 없음)
inline fun inlinedAction(block: () -> Unit) {
    println("Before action")
    block()
    println("After action")
}
```

---

- **비-로컬 반환(non-local return)** : 보통 람다 안의 `return`은 람다만 빠져나가지만, `inline` 함수에 전달된 람다는 코드가 호출 함수 안에 그대로 복사되므로 `return`이 **둘러싸는 함수 전체**를 종료시킴

```kotlin
inline fun findFirst(numbers: List<Int>, predicate: (Int) -> Boolean): Int? {
    for (number in numbers) {
        if (predicate(number)) return number   // findFirst 전체를 종료 (non-local return)
    }
    return null
}

val firstEven = findFirst(listOf(1, 2, 3, 4, 5)) { it % 2 == 0 }
println(firstEven)   // 2
```

- **`reified` 제네릭** : 보통 JVM의 타입 소거로 런타임에 `T`의 실제 타입을 알 수 없지만, `inline` 함수에서는 `reified`로 타입 정보를 유지할 수 있음

```kotlin
inline fun <reified T> isInstance(value: Any): Boolean = value is T

println(isInstance<String>("Hello"))   // true
println(isInstance<Int>("Hello"))      // false
```

---

- **`inline`을 쓰면 안 되는 경우**
  - 코드 크기 증가 : 호출 지점마다 본문이 복사되어 바이너리가 커지고 CPU 캐시 효율이 떨어질 수 있음
  - 큰 함수에는 부적합 : 로직이 많은 함수를 인라인하면 코드 비대화가 심해짐
  - 오버라이드 불가 : 컴파일 타임에 대체되므로 암시적으로 `final` — 서브클래스에서 재정의 불가
  - 람다가 없으면 효과 제한적 : 람다 매개변수가 없다면 얻을 이점이 적고, JIT 컴파일러가 더 잘 처리하는 경우가 많음
  - 재귀/`private` 함수에 부적합 : 재귀 함수는 인라인할 수 없고(컴파일 경고), `private` 인라인 함수는 호출 지점이 적어 효과가 제한적

---

- **Pro Tip: 인라인 프로퍼티** — getter/setter에 `inline`을 붙이면, 호출 지점에 getter/setter 코드가 그대로 삽입됨 (backing field가 있는 프로퍼티는 인라인 불가)

```kotlin
inline val isUserActive: Boolean
    get() = System.currentTimeMillis() - lastActivityTime < ACTIVE_THRESHOLD
// 접근할 때마다 메서드 호출 없이 계산 코드가 그 자리에 바로 삽입됨
```

  - 장점 : 메서드 호출 오버헤드 제거, 자주 접근하는 가벼운 연산에 유리
  - 한계 : backing field가 있으면 사용 불가, 복잡한 로직에 쓰면 바이트코드가 비대해짐

---

- **Pro Tip: `repeat()`/`map()`/`filter()`가 어떻게 `suspend` 람다를 받을 수 있는가**
  - 이 함수들은 모두 **`inline` 함수**라서, 전달된 `suspend` 람다 코드가 **호출 지점에 그대로 삽입**됨
  - 그 결과 람다가 별도 함수가 아니라 호출부(코루틴 컨텍스트 안)에 직접 자리하게 되어, 시그니처에 코루틴 관련 표시가 없어도 `suspend` 호출이 자연스럽게 동작함

```kotlin
suspend fun printMessage(message: String) = println("Message: $message")

suspend fun main() {
    repeat(3) { printMessage("skydoves $it") }   // repeat()는 inline이라 suspend 람다를 받을 수 있음
}
// 인라인 후 개념적으로:
// for (i in 0 until 3) { printMessage("skydoves $i") }
```

## 🔑 정리: 특징 · 장단점 · 예시

### 특징
- `inline`은 "함수 호출"이라는 개념 자체를 없애고, 코드를 호출 지점에 복사-붙여넣기 하는 컴파일 타임 최적화
- 이 복사 덕분에 비-로컬 반환, `reified` 제네릭, `suspend` 람다 수용처럼 **일반 함수로는 불가능한 기능**들이 열림

### 장점
- 람다마다 생기는 객체 생성·가상 호출 오버헤드를 없애, 자주 호출되는 고차 함수의 성능을 끌어올림
- `reified`로 런타임 타입 검사/캐스팅을 깔끔하게 구현할 수 있어 라이브러리 API 설계에 유리
- `return`이 람다가 아니라 함수 전체를 종료하게 만들어, 반복문 안에서 쓰는 것처럼 자연스러운 흐름 제어가 가능

### 단점
- 호출 지점마다 코드가 복사되므로, 큰 함수를 인라인하면 바이너리 크기가 눈에 띄게 늘어남
- `final`로 취급되어 상속/오버라이드 기반 설계와는 함께 쓸 수 없음
- 람다가 없는 함수에 `inline`을 붙이면 이점이 거의 없고, 오히려 JIT 컴파일러의 자체 최적화를 방해할 수도 있음

### 예시
```kotlin
// 비용이 작고 자주 호출되는 람다 기반 유틸 → inline이 적합
inline fun <T> measureAndRun(label: String, block: () -> T): T {
    val start = System.nanoTime()
    val result = block()
    println("$label took ${(System.nanoTime() - start) / 1_000_000}ms")
    return result
}

val data = measureAndRun("fetch") { fetchData() }
```
