## 0-13. Kotlin 가시성 수정자

- Kotlin은 `public`, `private`, `protected`, `internal` 네 가지 가시성 수정자를 제공. **수정자를 지정하지 않으면 기본값은 `public`**

| 수정자 | 접근 범위 |
|---|---|
| `public` | 어디서든 접근 가능 (기본값) |
| `private` | 같은 파일(최상위 선언) 또는 같은 클래스/객체 내부(멤버 선언) |
| `protected` | 클래스 멤버에만 적용. 선언한 클래스 + **서브클래스**에서 접근 가능 (최상위 선언엔 사용 불가) |
| `internal` | 같은 **모듈** 내에서만 접근 가능 |

```kotlin
class VisibilityExample {
    private val secret = "Hidden from the outside"        // 클래스 내부에서만
    fun revealSecret() = secret
}

open class Parent {
    protected fun protectedMethod() = "Accessible in subclasses"
}
class Child : Parent() {
    fun useProtected() = protectedMethod()                 // 서브클래스라 접근 가능
}

internal class InternalExample {
    internal fun internalFunction() = "Available within the module"   // 같은 모듈 어디서든
}
```

---

- **Pro Tip: `internal`이 바이트코드로 컴파일되는 방법**
  - JVM에는 "모듈" 단위 가시성이 없음 (`public`/`protected`/`private`/package-private만 존재)
  - 그래서 `internal` 선언은 바이트코드에서는 그냥 **`public`**으로 컴파일되고, 대신 함수/클래스 이름에 모듈 이름이 붙는 **네임 맹글링**(`aUsefulInternalFunction$MyLibrary_module`)이 적용됨
  - Java 쪽에서 보면 : 자동완성에 원래 이름이 뜨지 않아 사실상 숨겨짐 (맹글링된 이름으로 호출은 가능하지만 "쓰지 말라"는 강력한 신호)
  - 다른 Kotlin 모듈에서 보면 : 컴파일러가 메타데이터로 `internal`임을 인식해서, 접근하려고 하면 **컴파일 에러**로 막아줌 (맹글링 변환조차 시도하지 않음)

```kotlin
// MyLibrary 모듈
internal fun aUsefulInternalFunction() = println("internal util")

// 바이트코드 관점(개념적으로):
// public static final void aUsefulInternalFunction$MyLibrary_module() { ... }
```

  - 결과적으로 "Kotlin 컴파일러가 Kotlin 쪽 접근을 막고, 이름 맹글링이 Java/다른 JVM 언어 쪽 접근에 대한 방어막 역할"을 하는 이중 전략

## 🔑 정리: 특징 · 장단점 · 예시

### 특징
- 네 가지 수정자로 "누가 이 선언에 접근할 수 있는가"를 클래스 내부 / 같은 파일 / 서브클래스 / 같은 모듈 / 전체 공개 단위로 세밀하게 제어
- `internal`은 Kotlin만의 개념(모듈 단위)이라, JVM에는 없는 가시성을 네임 맹글링으로 흉내 내는 구조

### 장점
- 꼭 필요한 범위까지만 노출해서 캡슐화를 강화하고, 의도치 않은 외부 의존을 방지
- `internal`을 활용하면 라이브러리의 공개 API와 내부 구현을 명확히 분리할 수 있음
- `protected`로 상속 계층 안에서만 공유할 로직을 표현할 수 있어 Java의 package-private보다 의도가 더 명확함

### 단점
- `internal`은 "모듈"의 범위가 빌드 설정(Gradle 소스 셋 등)에 따라 달라질 수 있어, 생각보다 넓은 범위로 공개되는 경우가 있을 수 있음 (예: test 소스 셋은 main의 internal에 접근 가능)
- Java와 혼용되는 프로젝트에서는 `internal`이 사실상 `public` + 맹글링된 이름이라, Java 코드가 우회해서 접근할 여지가 완전히 막히지는 않음
- 가시성을 지나치게 세분화하면(모든 멤버에 다른 수정자) 코드를 읽을 때 "이게 왜 안 보이지?"를 추적하는 비용이 늘어날 수 있음

### 예시
```kotlin
class Repository internal constructor(private val api: ApiClient) {
    // 모듈 내부에서만 생성 가능 (internal 생성자)
    // api는 클래스 내부에서만 접근 가능 (private)

    fun fetchUser(id: String) = api.getUser(id)   // public: 모듈 밖에서도 호출 가능
}
```
